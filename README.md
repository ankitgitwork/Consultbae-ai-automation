# Consultbae AI Automation — Take-Home Assignment

A merged people database, a no-code duplicate-detection automation, and a
mini audio submission app, built across the 3 messy source files provided.

## What's in this repo

```
data/            The 3 raw source CSVs (naukri applicants, gig workers, CBNexus contacts)
db/              merge.py — Task 1: merges all 3 sources into one deduplicated SQLite DB
automation/      app.py — Flask API wrapping the matching logic; flow.json — exported n8n automation (Task 2)
audio-app/       app.py — Streamlit audio collection app (Task 3)
DATA_ISSUES.md   Full data issues report (Task 4) — 30 issues found and handled, auto-generated by merge.py
TASK5_SCALING.md Stretch writeup: what breaks scaling this to 5,000 workers in a weekend (Task 5)
```

## Setup — Task 1 (merge pipeline)

```
cd db
python merge.py
```

This reads all 3 files from `../data/`, matches people across sources
(email → phone → name, in that priority order), and writes `consultbae.db`
plus regenerates `DATA_ISSUES.md`. No external dependencies — standard
library only.

## Setup — Task 2 (automation)

The Flask API wraps the same matching logic as an HTTP endpoint so a
no-code tool can call it:

```
cd automation
pip install flask
python app.py
```

Runs on `http://localhost:5000`. `POST /check-duplicate` with a JSON body
(`name`, `email`, `phone`) returns whether that person already exists in
the database. `flow.json` is the exported n8n workflow: a webhook receives a
new submission, calls this API, and routes matches down a "duplicate found"
branch. To run the flow live, the local API needs to be reachable from the
internet (I used ngrok during development/testing).

## Setup — Task 3 (audio app)

```
cd audio-app
pip install streamlit pydub
python -m streamlit run app.py
```

Requires **ffmpeg** installed and on PATH (used to decode whatever format
the browser records in, and to compute audio properties). Opens at
`http://localhost:8501`. Submissions write into the same `db/consultbae.db`
from Task 1 — a worker who already exists (matched by phone number) gets
linked to their existing record rather than duplicated.

## Data issues report

See [`DATA_ISSUES.md`](./DATA_ISSUES.md) — generated automatically by
`merge.py` as it processes the 3 sources. 30 issues found, including
corrupted values, exact and near-duplicate rows, a malformed/column-shifted
row, a buried duplicate header, and 6 cases of different real people sharing
the same name (deliberately left unmerged rather than guessed).

## Stuck log

**1. pydub crashing on browser-recorded audio (`KeyError: 'sample_width'`).**
The Task 3 audio app worked fine against test files I generated myself, but
broke the moment I tested it with an actual browser microphone recording.
The error was a bare `KeyError: 'sample_width'` coming from inside pydub's
own code, not mine. I searched the exact error text and found this is a
known pydub issue: browser mic recordings are Opus-encoded, and Opus has no
fixed bit depth — when pydub can't get clean duration/format metadata from
ffmpeg's probe (common for live-recorded audio vs. a file with a proper
header), it falls back to parsing ffmpeg's text output with a regex that
expects a bit-depth field, and Opus's format string doesn't have one, so the
regex fails and pydub throws instead of handling it gracefully. Rather than
patch around pydub's internals, I asked myself what I was actually asking
pydub to do — guess a format — and just removed the guessing: I call ffmpeg
directly first to convert whatever comes in to a fixed, unambiguous 16-bit
WAV, and only ever hand pydub that clean file. I rejected two alternative
fixes I considered: downgrading pydub to an older version (didn't want an
unpinned dependency risk for something I couldn't fully explain), and trying
to force a specific format hint into pydub's loader (still routes through
the same broken parsing path for Opus specifically, so it wouldn't have
actually fixed anything).

**2. Database silently going "empty" after a file rename
(`consultbae.db.db`).** After moving files around between folders on
Windows, the audio app suddenly started throwing `no such table: people` —
which was confusing because the database clearly existed and had worked
minutes earlier. The key realization was that SQLite doesn't error when it
can't find a database file at the path it's given — it just silently
creates a new, empty one. So the actual bug wasn't in any of my code at
all; it was that the file on disk wasn't named what the code expected. I
tracked it down by having the app print the exact absolute path it was
trying to open, then checking that path's contents directly with
`Get-ChildItem ... | Select-Object Name, Length` instead of trusting what
File Explorer's default view showed — Windows had hidden the file
extension, so a rename that was meant to produce `consultbae.db` had
actually produced `consultbae.db.db`, and the visible label looked
identical to the correct name. Once I could see the real filename and byte
count side by side, the fix was a one-line rename.

**3. `pip`/`streamlit` not recognized despite installing successfully.**
Both `pip install X` and later running `streamlit run app.py` reported
"not recognized as a cmdlet" immediately after a clean install completed
without errors. This turned out to be a PATH issue — Python's own install
script was silently telling us the exact fix ("Consider adding this
directory to PATH"), but it's easy to scroll past that in a wall of
install output when you're looking for a hard error instead of a warning.
The reliable workaround I used throughout instead of fighting PATH config
was `python -m pip install X` and `python -m streamlit run app.py` —
running everything through `python -m` sidesteps needing the tool's own
script on PATH at all, since Python can find its own installed modules
directly.
